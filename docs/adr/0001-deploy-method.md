# ADR-0001. Развёртывание приложения с помощью deploy.sh

- **Статус: принято**
- **Дата: 2026-10-02**

## Контекст

Приложение TimeCapsule развёрнуто на одном экземпляре EC2. Исходный код хранится в GitHub.

При выпуске новой версии необходимо:

- получить новый код из репозитория;
- установить или обновить зависимости Composer;
- создать недостающие таблицы базы данных;
- перезагрузить PHP-FPM.

Выполнять все эти действия вручную при каждом обновлении неудобно и можно случайно пропустить один из шагов.

## Решение

Для развёртывания приложения используется скрипт `deploy.sh`, расположенный на EC2-сервере.

Скрипт выполняет следующие действия:

```bash
git pull --ff-only
composer install --no-dev --optimize-autoloader --no-interaction
php bin/init-db.php
sudo systemctl reload php-fpm
```

Скрипт запускается с локального компьютера через SSH:

```bash
ssh -i ~/.ssh/key.pem ec2-user@<Public-IP> ./deploy.sh
```

Использование set -euo pipefail позволяет остановить скрипт при возникновении ошибки.

Команда git pull --ff-only не позволяет автоматически объединять изменения, если файлы на сервере были изменены вручную.

## Рассмотренные альтернативы

### Копирование файлов через scp

Код можно было бы копировать с локального компьютера на сервер с помощью scp.

Преимущество этого способа — простота.

Недостатки:

- необходимо вручную выбирать и копировать файлы;
- можно случайно пропустить часть файлов;
- зависимости Composer не обновляются автоматически;
- обновление структуры базы данных нужно выполнять отдельно.

Поэтому этот способ неудобен для регулярного выпуска новых версий.

### Ручной git pull на сервере

Можно подключаться к серверу по SSH и вручную выполнять:
```bash
git pull
composer install
php bin/init-db.php
sudo systemctl reload php-fpm
```

Этот способ надёжнее копирования через scp, так как код берётся непосредственно из GitHub.

Однако каждый раз приходится выполнять несколько команд вручную, поэтому можно забыть один из этапов развёртывания.

### Скрипт deploy.sh

Скрипт `deploy.sh` выполняет все необходимые шаги автоматически и в одинаковом порядке.

Для выпуска новой версии достаточно одной команды SSH.

Этот вариант был выбран как наиболее удобный для текущего проекта.

## Последствия

Преимущества:

- деплой выполняется одной командой;
- уменьшается вероятность пропустить один из шагов;
- при ошибке скрипт прекращает выполнение;
- код на сервере соответствует версии из GitHub;
- после деплоя выводится последний установленный commit.

Недостатки:

- запуск деплоя всё ещё выполняется вручную;
- git pull обновляет файлы не атомарно;
- во время обновления пользователь может получить временно неконсистентную версию приложения;
- ошибки в коде могут попасть на сервер, если их не обнаружить до деплоя;
- откат требует git revert и повторного запуска deploy-скрипта.
