# ADR-0004. Размещение базы приложения в Amazon RDS

- **Статус:** принято.
- **Дата:** 2026-11-03.
- **Заменяет:** [ADR-0002](./0002-database-placement.md) в части размещения PostgreSQL на EC2.

## Контекст

В ЛР3 база TimeCapsule перенесена на отдельный EC2 `db-server` в приватной подсети `private-a` VPC `10.5.0.0/16`. PostgreSQL, ОС, резервные копии и восстановление требовали самостоятельного обслуживания. Для установки обновлений использовался временный NAT Gateway.

Приложение работает на `timecapsule-dev-app` в `eu-central-1a` и обращается к базе через приватное имя `db.timecapsule.internal`. Вложения уже хранятся в приватном Amazon S3 согласно [ADR-0003](./0003-attachment-storage.md.md).

Нужно уменьшить объём ручного обслуживания, обеспечить восстановление после ошибочного удаления данных и сохранить ограниченный сетевой доступ. Для учебной среды допустимы перерывы на обслуживание и ночная остановка; расходы должны контролироваться до завершения курса.

## Решение

Использовать **Amazon RDS for PostgreSQL 18.3, Single-AZ**, экземпляр `timecapsule-dev-rds` в регионе `eu-central-1`, зоне `eu-central-1a`.

| Параметр | Выбранное значение |
|---|---|
| Класс и хранилище | `db.t4g.micro`, `gp3`, 20 ГиБ |
| Автоматическое увеличение хранилища | Выключено |
| Группа подсетей | `timecapsule-dev-db-subnets` |
| Подсети группы | `private-a` — `10.5.10.0/24`, `private-b` — `10.5.11.0/24` |
| Публичный доступ | Выключен |
| Security Group RDS | `timecapsule-dev-rds-sg`: TCP/5432 только от `timecapsule-dev-web-sg` |
| Защита данных | TLS при подключении; шифрование хранилища; deletion protection |
| Пользователь и база приложения | `timecapsule` / `timecapsule`; административный пользователь — `dbadmin` |
| Автоматические резервные копии | Включены, срок хранения 7 дней |

В приватной зоне Route 53 прежняя A-запись заменена на CNAME:

```text
db.timecapsule.internal
  → timecapsule-dev-rds.cv4k8a882o6n.eu-central-1.rds.amazonaws.com
```

В приложении сохранено `DB_HOST=db.timecapsule.internal`. Пароль отдельного пользователя хранится в серверном `.env`, не публикуется и не включается в ADR.

Для остановки используется EventBridge Scheduler `timecapsule-dev-rds-nightly-stop`: `cron(0 23 * * ? *)`, часовой пояс `Europe/Chisinau`, Flexible time window `Off`. Роль `timecapsule-dev-scheduler-role` доверяет только `scheduler.amazonaws.com`; политика `timecapsule-dev-rds-stop` разрешает только `rds:StopDBInstance` для ARN этой базы. Перед занятием база запускается вручную.

Данные перенесены через `pg_dump --no-owner --no-privileges`; после сравнения количества пользователей и капсул приложение переключено на RDS. Проверена запись новой капсулы и работа без старого `db-server`, после чего старый EC2 завершён. Постоянная read replica не создаётся: учебные `lab5-db`, `lab5-db-replica` и `lab5-db-restore` удалены.

## Рассмотренные альтернативы

| Вариант | Обслуживание и доступность | Стоимость и ограничения | Вывод |
|---|---|---|---|
| **PostgreSQL на EC2** | Полный контроль над ОС и СУБД. Обновления, резервное копирование, репликация и восстановление организуются самостоятельно. Один сервер не защищает от отказа зоны. | EC2, EBS и временный NAT оплачиваются отдельно; требуется время на администрирование. | Подходит для специальных требований к ОС и расширениям, но сохраняет ручные обязанности ЛР3. |
| **RDS Single-AZ — выбран** | AWS обслуживает инфраструктуру и предоставляет автоматические резервные копии и PITR. Резервного экземпляра в другой зоне нет; при обслуживании возможна недоступность. | Один небольшой экземпляр и его хранилище. Поддерживается временная остановка. | Достаточно для учебного приложения с небольшой нагрузкой и допустимыми перерывами. |
| **RDS Multi-AZ DB instance** | Primary и синхронный standby в разных зонах; автоматическое переключение при отказе. Классический standby не обслуживает чтение. | Дополнительно оплачиваются резервные вычислительные ресурсы и хранилище. Один `app-server` всё равно остаётся отдельной точкой отказа. | Предпочтительнее для реальных пользователей с требованиями к доступности; для текущей лабораторной избыточен. |
| **Amazon Aurora PostgreSQL-Compatible** | Вычисления отделены от распределённого хранилища: копии данных размещены в трёх зонах. Reader в другой зоне может стать writer при отказе; для быстрой готовности вычислений его следует развернуть заранее. | Иная модель оплаты вычислений, хранения и, в зависимости от конфигурации, I/O. Нужно выбирать топологию кластера и проверять совместимость приложения. | Полезна для более высокой доступности и масштабирования, но усложняет текущую учебную конфигурацию. |

Свойства [RDS Multi-AZ](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Concepts.MultiAZSingleStandby.html) и [Aurora](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Concepts.AuroraHighAvailability.html) учитываются как альтернативы; эти конфигурации в лабораторной не развёрнуты. Ни реплика, ни standby сами по себе не защищают от ошибочного `DELETE`, поскольку передают изменения основной базы.

## Последствия

### Резервные копии и допустимая потеря данных

При работающем экземпляре RDS автоматически создаёт ежедневный снимок в назначенное окно резервного копирования. Журналы транзакций выгружаются примерно каждые пять минут; вместе со снимками они позволяют выполнить PITR в пределах доступного окна восстановления при политике хранения 7 дней. Во время остановки новые автоматические резервные копии не создаются.

При аварии могут быть потеряны изменения после `LatestRestorableTime`. Обычно отставание последней доступной точки составляет несколько минут, порядка пяти, но это не строгая гарантия максимальной потери: перед восстановлением необходимо проверить фактическое время. При логической ошибке выбирается момент **до** удаления данных. PITR создаёт отдельный экземпляр, который сначала проверяется, а затем используется для переноса данных или переключения приложения.

В лабораторной восстановлены четыре строки `notes` на точку `2026-10-30 19:41:00 UTC`. Проверка показала, что резервные копии позволяют вернуть предыдущее состояние, а read replica повторяет удаление.

Источники: [автоматические резервные копии](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_WorkingWithAutomatedBackups.html), [PITR и журналы транзакций](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PIT.html).

### Стоимость и ограничение расходов

Оценка составлена **3 ноября 2026** по публичному прайс-листу AWS для `eu-central-1`, PostgreSQL, Single-AZ, On-Demand. Версия прайс-листа — `20261029070635`, опубликована 29 октября 2026. Выбранные тарифы и расчёт приведены в таблице ниже; источник — [региональный прайс-лист AWS](https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AmazonRDS/current/eu-central-1/index.json).

| Компонент | Тариф | Оценка за месяц |
|---|---:|---:|
| `db.t4g.micro` при 730 часах работы | $0.019/час | $13.87 |
| 20 ГиБ gp3, выделенных весь месяц | $0.137 за ГиБ в месяц | $2.74 |
| **Базовая сумма при работе 24/7** | | **$16.61** |

Для другого времени работы `H` базовая оценка составляет **`0.019 × H + 2.74 USD/месяц`** при том же хранилище. Например, 80 оплачиваемых часов дают около **$4.26**. Это стоимость только RDS до налогов и применения кредитов; в неё не включены дополнительные CPU credits, резервные копии сверх включённого объёма, передача данных, необязательные платные функции и другие сервисы AWS.

Расходы уменьшаются за счёт небольшого класса, Single-AZ, ночной остановки, ручного запуска только для занятий и удаления учебных реплик и восстановленных копий. Хранилище остаётся ограниченным 20 ГиБ, поэтому свободное место нужно контролировать. При остановке плата за часы экземпляра прекращается, но сохраняется плата за выделенное хранилище и применимые расходы на резервные копии.

Через **7 суток непрерывной остановки AWS автоматически запускает RDS** для обслуживания. Ночное расписание должно снова остановить её в ближайшие 23:00; до этого вычислительные часы оплачиваются. Расписание и уведомления бюджета `ZeroSpend` из ЛР2 не являются жёстким пределом расходов: состояние RDS, успешность вызовов, остаток и сроки кредитов проверяются в Billing, RDS Events и CloudTrail. Для Paid plan использование сверх действующих кредитов оплачивается по тарифам AWS.

Источники: [региональный прайс-лист AWS](https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AmazonRDS/current/eu-central-1/index.json), [тарификация RDS PostgreSQL](https://aws.amazon.com/rds/postgresql/pricing/), [остановка и автоматический запуск](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_StopInstance.html), [уведомления AWS Budgets](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-managing-costs.html), [условия Paid plan](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/free-tier-plans.html).

### Поиск базы и отказ eu-central-1a

Приложение разрешает `db.timecapsule.internal` через DNS VPC и CNAME получает endpoint RDS. При обычном Stop → Start endpoint сохраняется, хотя приватный IP может измениться; поэтому A-запись на конкретный адрес RDS не используется. При восстановлении в новый экземпляр с другим endpoint нужно обновить CNAME, а `DB_HOST` приложения останется прежним.

При отказе `eu-central-1a` текущая Single-AZ база и находящийся там `app-server` могут стать недоступны. Наличие `private-b` в группе подсетей не создаёт standby и не включает автоматическое переключение. Для восстановления потребуется доступная резервная копия, новый RDS в `eu-central-1b`, проверка данных и обновление CNAME; также потребуется развернуть приложение в доступной зоне, восстановить его настройки и переназначить Elastic IP. Вложения останутся во внешнем S3.

Для автоматического переживания отказа зоны понадобятся Multi-AZ или подходящий кластер Aurora, а также несколько серверов приложения в разных зонах и балансировщик. В текущей учебной архитектуре такой отказ требует ручного восстановления, а его продолжительность зависит от запуска базы и приложения.

### Обязанности и компромиссы

AWS обслуживает ОС и инфраструктуру RDS и выполняет настроенные операции резервного копирования. За владельцем приложения остаются права пользователей, защита секретов, Security Groups, схема, миграции, выбор настроек обслуживания, проверка восстановления и контроль расходов. RDS уменьшает объём администрирования, но не устраняет ошибки приложения, SQL-ошибки и необходимость планировать отказ зоны.
