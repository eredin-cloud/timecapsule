# ADR-0005. Хранение пользовательских сессий в Amazon DynamoDB

- **Статус:** принято.
- **Дата:** 2026-11-05.

## Контекст

TimeCapsule использует PHP-сессии для хранения состояния входа и CSRF-токена. До ЛР6 сессии сохранялись в файлах `storage/sessions/` на одном `app-server`. После перехода к Application Load Balancer и группе Auto Scaling запросы пользователя могут попадать на разные экземпляры; при уменьшении группы отдельный сервер и его локальные данные удаляются.

Нужно сохранять вход независимо от выбранного сервера и его жизненного цикла. Для учебной среды используются регион `eu-central-1`, от двух до четырёх серверов `t3.micro`, общая RDS PostgreSQL и приватный S3. Новый способ должен поддерживаться существующим AWS SDK для PHP и получать права через роль EC2 без статических ключей доступа.

## Решение

Хранить сессии в региональной таблице **Amazon DynamoDB `timecapsule-dev-sessions`**, режим ёмкости **On-demand**. Partition key — `id` типа `String`, sort key отсутствует. Для автоматического удаления устаревших элементов включён TTL по атрибуту `expires`.

В `src/bootstrap.php` до `session_start()` регистрируется обработчик `Aws\DynamoDb\SessionHandler::fromClient(...)` с параметром `table_name`. Имя таблицы читается из `DYNAMODB_SESSION_TABLE`, регион — из `AWS_REGION`. Значения ключа, данных и срока действия обработчик записывает в атрибуты `id`, `data` и `expires`; cookie `timecapsule_session` содержит идентификатор сессии, а не её содержимое.

Каждому серверу через шаблон `timecapsule-dev-app-lt` назначается профиль роли `timecapsule-dev-app-role`. Политика `timecapsule-dev-app-sessions` разрешает только `GetItem`, `PutItem`, `UpdateItem` и `DeleteItem` для одной таблицы. Приложение не создаёт таблицу и не сканирует её для очистки: схема и TTL настраиваются отдельно, а временные учётные данные предоставляет роль EC2.

Для сохранения входа привязка пользователя к конкретному серверу не требуется. Серверы обращаются к общей таблице по HTTPS через региональный endpoint DynamoDB; в текущем размещении публичные подсети, маршрут через Internet Gateway и автоматически назначенные IPv4 обеспечивают исходящий доступ. Отдельный VPC endpoint в этой работе не создаётся.

## Рассмотренные альтернативы

| Вариант | Поведение при масштабировании и отказах | Обслуживание и расходы | Вывод |
|---|---|---|---|
| **Файлы на сервере + sticky sessions** | ALB старается направлять запросы пользователя на один сервер. При отказе или удалении этой цели выбирается другая, но локальный файл сессии туда не переносится, поэтому вход может потеряться. | Отдельное хранилище не оплачивается, но состояние привязано к экземплярам и усложняет их замену. Привязка также ограничивает свободное распределение запросов. | Просто для одного сервера; не удовлетворяет требованию сохранять вход при уменьшении группы. |
| **Таблица в RDS PostgreSQL** | Общее хранилище доступно всем серверам; требуется обработчик сессий и настройка очистки истёкших записей. Доступность сессий зависит от существующей RDS Single-AZ. | Использует уже оплачиваемую базу, но добавляет обращения, подключения и конкуренцию за её ресурсы. TTL нужно реализовать отдельным механизмом. | Рабочий вариант с транзакциями SQL, но увеличивает нагрузку и обязанности вокруг основной базы. |
| **DynamoDB — выбран** | Общая таблица не зависит от диска и жизненного цикла EC2; региональная DynamoDB устойчива к отказу отдельной зоны. AWS SDK для PHP уже предоставляет обработчик сессий. | Нет отдельного экземпляра БД для сессий; оплачиваются запросы и хранение. On-demand не требует выбора provisioned capacity, TTL выполняет фоновую очистку. | Подходит для обращения по идентификатору сессии и взаимозаменяемых серверов Auto Scaling. |

## Последствия

### Сохранение входа и ограничения доступности

В заданиях 5–6 подтверждено сохранение входа при смене сервера в Served by и при изменении размера группы с 2 до 4 и обратно до 2. Завершение экземпляра не удаляет сессию, поскольку данные находятся в DynamoDB.

Доступность таблицы не делает всё приложение независимым от зоны. RDS `timecapsule-dev-rds` остаётся Single-AZ в `eu-central-1a`, и при её недоступности запросы к капсулам и проверка `/health` завершаются ошибкой. Решение о размещении основной базы описано в [ADR-0004](./0004-database-hosting.md); Multi-AZ RDS в этой лабораторной не включалась.

### Срок действия и очистка

Обработчик записывает `expires` как Unix timestamp в секундах и использует `session.gc_maxlifetime` PHP, если отдельный срок жизни не задан. При чтении он проверяет срок действия и не принимает истёкшую сессию. TTL удаляет элементы асинхронно, поэтому наличие старой строки в таблице не означает, что такая сессия продолжает действовать.

Стандартная конфигурация обработчика использует согласованное чтение; блокировки сессий по умолчанию выключены. При появлении конкурирующих запросов, меняющих одну сессию, потребуется отдельно оценить необходимость блокировок и их влияние на задержки и число операций.

### Расходы и безопасность

On-demand оплачивается по фактическим запросам и объёму хранения; это не бесплатный режим и не жёсткий предел расходов. TTL ограничивает накопление устаревших сессий, но не ограничивает поток новых запросов. Таблица сохраняется после занятия; отсутствие отдельного экземпляра устраняет необходимость останавливать сервер сессий.

Политика ограничена одной таблицей и четырьмя действиями с элементами. Статические AWS-ключи не сохраняются в `.env` или AMI. Содержимое сессии и полный идентификатор действующей сессии не публикуются в отчёте.

AMI содержит одинаковый код и `.env` для всех экземпляров, поэтому образ остаётся приватным. При изменении конфигурации или секретов нужно обновлять образ и экземпляры группы.
