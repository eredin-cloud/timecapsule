# ADR-0002: Размещение базы данных

## Статус

Принято.

## Контекст

В ЛР2 приложение TimeCapsule и PostgreSQL работали на одном EC2-сервере. Такая схема проста, но приложение и база данных не изолированы друг от друга и имеют общую точку отказа.

В ЛР3 приложение переносится на отдельный `app-server`, а база данных должна быть размещена отдельно. Необходимо выбрать вариант, который обеспечит безопасный доступ к PostgreSQL и не будет напрямую открывать базу в интернет.

Рассматривались три варианта размещения базы данных.

### Вариант 1. База на одном сервере с приложением

PostgreSQL работает непосредственно на `app-server`, как в ЛР2.

Преимущества:

- самая простая архитектура;
- не требуется сетевое подключение между приложением и базой;
- меньше EC2-ресурсов и ниже стоимость.

Недостатки:

- приложение и база имеют одну точку отказа;
- нагрузка приложения и базы конкурирует за ресурсы одного сервера;
- база находится на сервере, который доступен из публичной сети;
- сложнее независимо обслуживать и масштабировать приложение и базу данных.

### Вариант 2. Отдельный сервер базы в публичной подсети

PostgreSQL размещается на отдельном EC2-сервере в публичной подсети с маршрутом к Internet Gateway.

Преимущества:

- приложение и база разделены;
- сервер базы можно обслуживать и масштабировать независимо;
- обновления пакетов можно получать напрямую из интернета.

Недостатки:

- сервер базы находится в публичной подсети;
- при ошибке в Security Group база может оказаться доступной из интернета;
- наличие публичного маршрута увеличивает поверхность атаки.

### Вариант 3. Отдельный сервер базы в приватной подсети

PostgreSQL размещается на `timecapsule-dev-db` в приватной подсети `timecapsule-dev-private-a`.

Доступ к порту PostgreSQL разрешён только от Security Group приложения `timecapsule-dev-web-sg`. Дополнительно доступ ограничивается правилами `pg_hba.conf`.

Для подключения приложение использует приватное DNS-имя:

```text
db.timecapsule.internal
```

Преимущества:

- база данных не имеет прямого доступа из интернета;
- порт PostgreSQL доступен только серверу приложения;
- приложение и база изолированы друг от друга;
- базу можно обслуживать независимо;
- приватное DNS-имя позволяет не привязывать приложение к конкретному private IP.

Недостатки:

- архитектура становится сложнее;
- для установки системных обновлений требуется временный NAT Gateway;
- появляется дополнительная стоимость отдельного EC2-сервера и временного NAT Gateway.

## Решение

Выбран вариант размещения PostgreSQL на отдельном сервере `timecapsule-dev-db` в приватной подсети `timecapsule-dev-private-a`.

Приложение `timecapsule-dev-app` обращается к базе по приватному DNS-имени:

```text
db.timecapsule.internal
```

База данных не имеет публичного IPv4-адреса и не имеет постоянного маршрута в интернет.

Доступ к PostgreSQL ограничен несколькими уровнями защиты:

1. `db-server` находится в приватной подсети.
2. Security Group базы разрешает порт `5432` только от Security Group приложения.
3. `pg_hba.conf` разрешает подключение только пользователю `timecapsule` к базе `timecapsule`.
4. Для PostgreSQL используется отдельный сильный пароль.

## Последствия

База данных не имеет постоянного выхода в интернет. Когда необходимо установить системные обновления, временно создаётся NAT Gateway в публичной подсети `timecapsule-dev-public-a`, а в `timecapsule-dev-private-rt` добавляется маршрут:

```text
0.0.0.0/0 -> NAT Gateway
```

После выполнения обновлений маршрут, NAT Gateway и выделенный для него Elastic IP удаляются.

Такой подход позволяет не держать NAT Gateway постоянно только ради редких обновлений базы. NAT Gateway оплачивается за время работы и объём обработанного трафика, поэтому его временное создание уменьшает постоянные расходы.

`app-server` имеет Elastic IP, потому что пользователи сейчас подключаются непосредственно к этому EC2-серверу. Постоянный публичный адрес позволяет сохранить неизменными адрес приложения и значение `APP_URL` после остановки и повторного запуска экземпляра.

В дальнейшем, когда перед `app-server` появится Load Balancer, пользователи будут обращаться к балансировщику, а не непосредственно к EC2. В этом случае отдельный Elastic IP для `app-server` больше не потребуется, и сервер приложения сможет работать без постоянного публичного адреса.

Выбранная архитектура сложнее варианта из ЛР2, но лучше разделяет ответственность компонентов, уменьшает доступность базы данных из внешней сети и позволяет независимо обслуживать приложение и PostgreSQL.
